## Context and project contribution

LongMemEval and LoCoMo study long-term conversational-memory performance on benchmark tasks and histories (Wu et al., 2025; Maharana et al., 2024). This project focuses on a complementary workflow: derive tests from an authorised conversation, let an operator confirm the reference facts, run a target with controlled memory settings, and preserve the evidence used to judge each answer. The contribution is the auditing workflow and its evidence controls, not a new foundation model or a claim to replace those benchmarks. Experiment C is a limited compatibility check against LongMemEval, not a full benchmark result.

[Mem0](https://arxiv.org/abs/2504.19413) studies memory extraction, consolidation and retrieval, including a graph variant; [Zep](https://arxiv.org/abs/2501.13956) describes a temporal knowledge-graph architecture for maintaining agent memory. Their primary purpose is to provide memory infrastructure, whereas this prototype tests an observable target against operator-reviewed source evidence. This distinction does not establish that either system lacks auditing features, or that the prototype outperforms them. Our experiments do not run a controlled head-to-head comparison with Mem0 or Zep, and their published benchmark scores cannot be compared directly to our selected samples and scoring rules.

## 1. System and experimental workflow

The prototype is a React web application with a FastAPI backend and PostgreSQL persistence. It supports source-history intake, memory extraction, operator confirmation of ground truth, test generation and review, a controlled target-memory store, model-backed answering, response assessment, evidence inspection, and JSON/CSV/reproduction exports.

For the UI experiment, OpenRouter `openai/gpt-6-luna` was the target model. The source history and expected behaviours were synthetic. Candidate memories were confirmed in the app before testing. Both conditions used the same confirmed memory set and saved question suite. The compared setting changed from **First-match retrieval** to **Relationship-priority retrieval**; the recorded setting is a policy package, so the result should not be attributed to one isolated retrieval switch. No model weights were trained or changed.

The evaluator used a semantic assessment with an evidence-rule cross-check. A disagreement was left **Uncertain** rather than silently counted as a pass or fail. The saved audit report retains each original automated verdict; reference labels are stored separately. This separation is important: the reference-reviewed chart is an additional view, not an edit to the original automated report.

### Synthetic case and frozen questions

The seven user messages established: Wellington as the user’s city; Python as a general preference; MySQL as the Harbour capstone backend’s original database; Java as a Harbour-specific requirement; PostgreSQL as the current database replacing MySQL; and conflicting, still-active Harbour production-region sources (North and South) that require clarification.

| Ability | Test question | Expected behaviour |
|---|---|---|
| Accuracy | What city does the user live in? | Answer Wellington. |
| Freshness | Which database applies now, and which earlier system did it replace? | Answer PostgreSQL; identify retired MySQL as the predecessor. |
| Conflict Resolution | What should be clarified about the Harbour production region before acting? | State that the active plan says North and the signed brief says South; ask which controls. |
| Appropriate Use | Which backend language should be recommended for Harbour, and how does that relate to unrelated projects? | Recommend Java for Harbour; keep Python as a general preference for unrelated work. |

Each condition ran the same four questions three times: six completed runs and 24 saved target answers. Repeated calls share the same history and questions; they are not 24 independent scenarios.

## 6. What the results establish

- The working system can carry an operator-confirmed source-backed synthetic case through four test abilities, repeated target runs, automated assessment, reference review, and a visible before/after comparison.
- In the GPT‑6 Luna case, the changed memory policy improved the target’s tested pass rate from 25% to 75%; the gains were limited to Conflict Resolution and Appropriate Use.
- The Auditor’s hybrid evaluation withheld a verdict on 7/24 answers when its two checks disagreed, and the app exposed those cases for source-based review.
- The current-source GPT‑6 Luna repair comparison completes the tutor’s diagnosis → repair → same-test retest workflow in the running system. On six shared decided questions, targeted retrieval passed 3/6 versus 1/6 under the original; it passed two questions that the original failed and regressed on none. The targeted full run passed 4/7 decided answers and left one uncertain, while five answers across all three current-source conditions remain uncertain. This is one synthetic history and one run per condition, with automatic grades.
- The separate earlier-source GPT‑6 Luna repair comparison repeated the tutor workflow three times on a four-question synthetic suite; targeted retrieval passed 9/9 decided candidate answers and left 3/12 candidate answers unresolved. Its source digest differs from the delivered application, so it remains historical support.
- The separate Qwen study demonstrates a diagnosis-guided repair and same-suite retest. Its results are promising but exploratory.
- The current-source same-suite repeat showed higher results for Relationship-priority retrieval than First-match retrieval in all three repeated pairs: First-match retrieval 3/24 pass, 16 fail, 5 uncertain; Relationship-priority retrieval 15/24 pass, 4 fail, 5 uncertain. This is synthetic engineering evidence with automatic grades, not formal acceptance. The earlier extraction-failure record and separate post-fix intake retest are reported independently.
- A separate post-fix intake retest completed all three OpenRouter GPT‑6 Luna agent roles and produced 14 candidate memories; two advisory items were surfaced and the 14 candidates were subsequently confirmed using the returned reviews. This is an extraction-stage engineering check, not a target-behaviour or independent-validity result.
- Proposal B and the archived LongMemEval C collection both rank relationship-priority retrieval above first-match retrieval in each of three repetitions, so their directional ranking agreement is 3/3 on these saved collections. This supports the proposal’s local consistency check; it is not an independent estimate of Auditor reliability or a full-benchmark result.
- The system does **not** establish Auditor reliability across populations of real users or domains. In the earlier held-out experiment described in this section, two operating targets were missed; the later paired retest at the top of this report met the descriptive thresholds on its selected synthetic sample. Both reviews were reported as independent and blind but AI-assisted; identity and independence are not independently authenticated.

## 7. Limitations and next experiment

The current-source diagnosis-led retest uses one short synthetic history, one target model, eight questions, and one execution per condition; five of 24 labels are uncertain, the shared paired comparison uses six decided questions, and automatic assessments are not independent references. Its diagnostic model report does not establish cause. The earlier-source GPT‑6 Luna retest uses four questions and three correlated executions per condition; run order was not randomised and provider sampling may vary. The Qwen study is also small, synthetic, and not independently labelled.

The automated A/B/C collections, including the expanded 30-case C comparison, do not need to be rerun merely to produce missing human labels. The source-grounded AC1 and AC2 paired reviews and the four-strategy B blind reviews have since been received and analysed, as described above. The user subsequently confirmed that all data, including the later AI-generated findings, were individually human-reviewed. Remaining substantive evidence issues and disagreements stay visible, and the B threshold-freeze record still requires verification; the confirmation does not itself supply new item-specific adjudications. The latest A review mapped only failures corresponding to its frozen inventory; the other failed answers must not be treated as inventoried defects. If that record cannot establish a pre-outcome freeze, a new held-out run must use a threshold and protocol frozen first. At least two eligible reviewers should independently label the held-out answers and adjudicate disagreements. Report coverage and abstentions alongside accuracy and failure recall; treat source histories, not repeated answers, as the main unit for uncertainty estimates.
